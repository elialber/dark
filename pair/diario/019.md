## Decisões tomadas aqui, para confirmar

Registradas em `docs/decisoes.md`:

1. **`sh`:** continua `sh -c`; no Windows, procura no `PATH` e depois ao
   lado do git (Git for Windows); sem nenhum, diz o que instalar ou
   pede o comando em lista.
2. **UTF-8 na saída:** só quando o fluxo não está em UTF-8, e nunca
   contra um `PYTHONIOENCODING` definido pelo usuário. Os erros mantêm a
   política do fluxo.
3. **Retenção:** política gerenciada antes do usuário; aviso contado a
   partir de agora, não do `--ate`.
4. **Intervalo testado:** constante do leitor, 2.1.295 a 2.1.326.
5. **Diretório temporário que não sai:** cinco tentativas, depois aviso
   no resultado da validação, em vez de exceção.
6. **`evals/git` com `surrogateescape`:** como o `git_history`, para que
   nomes de arquivo voltem ao git intactos; `cli._git` usa `replace`,
   porque só lê hashes e o código de saída.

## O que não foi exercitado em Windows e macOS

O CI roda os testes, que usam só dados sintéticos e repositórios git
criados na hora. Ficou sem exercício:

- **Transcrições reais do Claude Code no Windows**: a regra da pasta de
  projeto (S1.1), a forma do `cwd` e das chaves de `projects` no
  `.claude.json` (S1.3), e se existe ferramenta de PowerShell que faça
  commits (S3.7).
- **O Claude Code real no Windows**: `claude.cmd` resolvido por
  `shutil.which` é testado com executável falso; nunca rodou o
  `/context` de verdade lá.
- **Git for Windows sem a pasta `bin` no `PATH`**: no executor do GitHub
  o `sh` está no `PATH`, então a busca ao lado do git só foi testada com
  uma árvore falsa.
- **`taskkill /T`** com uma árvore de verdade só é exercitado por
  `test_timeout_kills_child_processes`, com um filho do `sh`; não com
  `pytest` ou `npm`, que criam muitos processos.
- **Saída redirecionada no Windows de verdade**: o teste simula o fluxo
  cp1252 dentro do Python; o CI captura a saída pelo pytest.
- **macOS com dados reais**: esta sessão rodou a auditoria uma vez no
  macOS (sem erro). Não foram exercitados `/tmp` → `/private/tmp` (S1.4),
  sistema de arquivos sem diferença de maiúsculas (S1.3) nem o git da
  Apple (S4.3).
- **Desempenho**: os testes levam 77 a 90 s no Windows, contra 12 s no
  Ubuntu; uma auditoria real no Windows não foi medida.

Recomendação, em ordem:

1. Um teste de fumaça no CI que rode `dark auditar --todos` sobre os
   sintéticos com a saída redirecionada para arquivo (`> relatorio.md`)
   em cada sistema, e confira que o arquivo é UTF-8 e tem o `→`. É o uso
   principal e fica coberto de ponta a ponta.
2. Um job no Windows que tire a pasta `bin` do Git do `PATH` antes de
   rodar `test_evals.py`, para exercitar a busca do `sh` ao lado do git.
3. Uma sessão manual curta no Windows, com `CLAUDE_CONFIG_DIR`
   descartável, que grave duas ou três transcrições num repositório com
   acento e espaço no caminho. Com elas, viram arquivos sintéticos novos
   que fixam S1.1 e S1.3.
4. O mesmo no macOS, num repositório sob `/tmp` e com nome em maiúsculas
   diferentes do digitado.
