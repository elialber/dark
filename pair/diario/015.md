## As três suposições mais perigosas

1. **S7.2: o histórico é o que está no disco.** O Claude Code apaga as
   transcrições depois de 30 dias por omissão. O relatório diz "todo o
   histórico" e `--dias 90` devolve 30 dias, sem aviso. Vale em qualquer
   sistema, para todo usuário que não mudou o ajuste, e é invisível:
   nenhum número fica estranho.
2. **S3.3: sem arquivo e sem prefixo é embutida.** Funciona nesta
   máquina porque os nomes batem com os do diário 009. Em outra, uma
   skill de usuário apagada no meio do período vira "plataforma" e sai de
   "O que chama atenção", que é a parte do relatório que diz onde mexer.
   O erro aponta para o lado contrário do que o relatório quer mostrar.
3. **S2.1: o formato da versão seguinte.** O leitor exige campos que o
   Claude Code não promete manter. Uma renomeação faz todas as sessões
   virarem falha (visível); a perda de um campo opcional
   (`api-request-shape`, `gitOperation`) faz uma seção inteira perder
   dados sem aviso específico (invisível). O usuário em outra máquina
   provavelmente tem outra versão.

Para Windows, o que mais pesa é S6.6: o uso mais simples, `dark auditar >
relatorio.md`, quebra.

## O que não deu para avaliar só lendo o código

- **Regra da pasta de projeto em Windows e com caracteres fora do
  ASCII** (S1.1): é do Claude Code, e não há documentação. Precisa de uma
  sessão real no Windows (ou do código-fonte do Claude Code).
- **Forma das chaves de `projects` no `.claude.json` no Windows** (S1.3):
  barra, letra de unidade.
- **Em que forma o Claude Code grava o `cwd`** com link simbólico no
  caminho (S1.4): resolvido ou como digitado.
- **Pontos de entrada além da linha de comando** (S2.2): se o aplicativo
  de desktop e as extensões de IDE gravam no mesmo lugar e no mesmo
  formato; o que `entrypoint` traz neles.
- **Ferramenta de PowerShell no Windows** (S3.7): se existe na versão em
  uso e se commits passam por ela.
- **Canais de política gerenciada além do diretório** (S1.7): perfil no
  macOS, registro no Windows.
- **Prefixos da conta em organização ou em outro plano** (S3.4).
- **Saída traduzida do `/context`** (S6.3).
- **Comportamento em disco de rede e pasta sincronizada** (S1.5): só o
  `/mnt/c` do WSL foi medido.
- **O fator de caracteres por token em instruções de outro idioma**
  (S3.5): dá para medir com dados, não lendo código.
- **Desempenho real no Windows:** os testes levaram 70 s, contra 10 s
  no Ubuntu e 30 a 37 s no macOS. Isso indica que criar processo git é
  bem mais caro lá, mas uma auditoria real não foi medida.
