### O ciclo

1. **Plano.** `Plan(module, version, operations)`. `inspect` calcula tudo
   numa camada em memória e devolve, por operação, `new`,
   `already_applied`, `already_present` ou `conflict` (com motivo em
   português), mais um diff unificado por arquivo. Não grava nada.
2. **Aplicação.** `apply` faz o mesmo cálculo. Se houver um conflito,
   não grava nada e devolve o relato. Senão grava tudo de uma vez:
   cria diretórios, grava arquivos (arquivo temporário mais
   `os.replace`, preservando o modo), remove o que for preciso. Se uma
   gravação falhar no meio, o que já foi gravado é desfeito e o erro sobe.
3. **Manifesto.** `.dark-scaffold.json` na raiz do repositório.
4. **Reversão.** `revert(repo, módulo)` desfaz as entradas do módulo da
   última para a primeira, também numa camada em memória e gravando tudo
   no fim. Quando o manifesto fica vazio, ele é apagado.

## Formato do manifesto

JSON, UTF-8, indentação de 2, LF. Uma entrada por operação efetivamente
aplicada, na ordem de aplicação:

- `module`, `version`: quem pediu, com a versão fixada;
- `op`: a operação, no mesmo formato do arquivo de plano;
- `owned`: o que a operação teve de criar no caminho e deve limpar ao
  sair, na ordem de criação. Tipos: `dir` (diretório); `file` (o arquivo,
  com o `skeleton`, o conteúdo inicial: `""` para texto, `"{}\n"` para
  JSON); `json_key` (uma chave criada como contêiner vazio); `json_inner`
  (o espaço que havia dentro de um contêiner JSON vazio antes do primeiro
  filho, para devolvê-lo igual);
- `sha256`: só em `create_file`, o hash do conteúdo gravado;
- `shared: true`: a operação já estava presente porque outro módulo a
  aplicou. A entrada registra a necessidade, não uma mudança.

Exemplo sintético: o módulo `exemplo` 0.3.1 acrescenta um servidor a um
`.mcp.json` que não existia, um arquivo inteiro e uma linha a um
`.gitignore` que já existia; o módulo `outro` 1.0.0 pede a mesma linha.

```json
{
  "format": "dark-scaffold/1",
  "entries": [
    {
      "module": "exemplo",
      "version": "0.3.1",
      "op": {"op": "json_entry", "path": ".mcp.json", "keys": ["mcpServers"],
             "key": "exemplo",
             "value": {"command": "exemplo-mcp",
                       "env": {"EXEMPLO_TOKEN": "${EXEMPLO_TOKEN}"}}},
      "owned": [
        {"kind": "file", "path": ".mcp.json", "skeleton": "{}\n"},
        {"kind": "json_inner", "path": ".mcp.json", "keys": [], "inner": ""},
        {"kind": "json_key", "path": ".mcp.json", "keys": ["mcpServers"]},
        {"kind": "json_inner", "path": ".mcp.json", "keys": ["mcpServers"], "inner": ""}
      ]
    },
    {
      "module": "exemplo",
      "version": "0.3.1",
      "op": {"op": "create_file", "path": ".exemplo/config.toml", "content": "ativo = true\n"},
      "owned": [{"kind": "dir", "path": ".exemplo"}],
      "sha256": "…hash de 'ativo = true\\n'…"
    },
    {
      "module": "exemplo",
      "version": "0.3.1",
      "op": {"op": "append_line", "path": ".gitignore", "line": ".exemplo/"},
      "owned": []
    },
    {
      "module": "outro",
      "version": "1.0.0",
      "op": {"op": "append_line", "path": ".gitignore", "line": ".exemplo/"},
      "owned": [],
      "shared": true
    }
  ]
}
```

(O arquivo real sai com uma chave por linha; aqui está compactado para
leitura. A saída real de um caso parecido foi conferida pelo comando.)

Reverter `exemplo` aqui: a linha do `.gitignore` passa para `outro`, que
vira dono, sem `shared` (status "repassado"); o arquivo é apagado porque
o hash bate, e `.exemplo/` sai por estar vazio; no `.mcp.json`, a
entrada `exemplo` sai, `mcpServers` volta a `{}`, a chave sai, a raiz
volta a `{}` e o arquivo, igual ao esqueleto, é apagado.

## Decisões de projeto, para confirmar

1. **Texto emendado, nunca reescrito.** Nenhum arquivo é gravado a partir
   de um modelo interpretado. O motor decodifica, insere ou retira um
   trecho e codifica de volta. Para JSON, um analisador próprio
   (`jsontext.py`) guarda a posição de cada valor; a inserção copia a
   indentação, o separador de chave e a quebra de linha que o arquivo já
   usa, e a remoção corta exatamente o trecho que a inserção acrescentou.
   É isso que garante a volta byte a byte com a formatação original. O
   custo: JSON com comentários (JSONC) é recusado como "JSON inválido".
2. **Inserção sempre no fim** (do objeto, da lista, do arquivo). A
   remoção é o inverso exato: com irmão anterior, corta da vírgula dele
   até o fim do próprio valor; sendo o primeiro, corta até o próximo
   irmão; sendo o único, esvazia o contêiner, e o `json_inner` devolve o
   espaço que havia.
3. **Posse e repasse.** O que uma operação cria no caminho (diretório,
   arquivo, chave, espaço interno de contêiner) fica registrado como dela.
   Na reversão, cada coisa é: repassada a outra entrada do manifesto que
   ainda dependa dela; senão, removida se voltou a vazia; senão, deixada
   e relatada. É o que dá a reversão parcial no mesmo arquivo e no mesmo
   diretório, em qualquer ordem.
4. **Necessidade compartilhada.** Quando um módulo pede o que outro já
   aplicou (mesma operação, ou um diretório que outro criou no caminho),
   o motor grava uma entrada `shared`. Ao reverter o dono, a posse passa
   para quem compartilha, em vez de desfazer.
5. **Arquivo criado inteiro tem dono único.** Outro módulo não pode
   acrescentar linha, bloco ou entrada JSON num arquivo que um módulo
   criou com `create_file`: é conflito. Sem essa regra, reverter o dono
   antes do outro deixava o arquivo (o hash não bate) até uma segunda
   reversão. O mesmo módulo pode.
6. **Edição do usuário.** O motor só desfaz quando encontra exatamente o
   que aplicou: o hash do arquivo, o valor JSON (comparado como valor,
   não como texto), o conteúdo do bloco entre os marcadores. Se mudou, a
   entrada fica no manifesto com status "mantido" e motivo. Se o usuário
   já removeu a coisa, o status é "já ausente" e a entrada sai. Recursos
   que ficaram com conteúdo do usuário (diretório com arquivos dele,
   objeto JSON com chaves dele) são deixados e relatados em "aviso".
7. **"Já aplicado" e "já presente".** O primeiro quando o manifesto
   registra a operação para o mesmo módulo; o segundo quando a coisa
   já existia por conta do usuário. Neste caso nada é registrado e a
   reversão não toca nela. Registrado mas ausente do repositório é
   conflito ("reverta o módulo antes de aplicar de novo").
8. **Caminhos.** Lidos com `PureWindowsPath` (que aceita os dois
   separadores) e gravados em forma POSIX via `as_posix`, para o
   manifesto valer em qualquer sistema. Recusados: absoluto, com unidade,
   com `..`, dentro de `.git`, o próprio manifesto e qualquer caminho que
   passe por um link simbólico existente, **mesmo um que aponte para
   dentro do repositório** (gravar por um link edita um arquivo que o
   plano não nomeou). Um caminho que ainda não existe é conferido no
   ancestral mais próximo que existe.
9. **Codificação.** Pela marca de ordem de bytes (UTF-8, UTF-16,
   UTF-32), depois UTF-8 estrito, por fim Latin-1. Latin-1 decodifica
   qualquer sequência e devolve os mesmos bytes, então serve para emendar
   ASCII em arquivo de codificação desconhecida; texto não ASCII nesse
   caso é recusado. A quebra de linha é a da primeira linha do arquivo;
   arquivo novo usa LF. Arquivo sem quebra no fim continua sem.
10. **Segredos.** `env_ref("NOME")` produz `${NOME}`, a forma que o
    Claude Code expande no `.mcp.json`; o motor nunca expande. Além
    disso, uma operação cujo texto contenha o valor de uma variável de
    ambiente com nome de segredo (`KEY`, `TOKEN`, `SECRET`, `PASSW`,
    `CREDENTIAL`, `AUTH`, `PRIVATE`) e com 8 caracteres ou mais é
    conflito, e o motivo cita o nome, nunca o valor. Variáveis com outros
    nomes não são vigiadas, para não recusar `/home/...` ou `en_US.UTF-8`.
11. **Versão fixada.** A versão do plano precisa ser exata (`1.2.0`,
    `0.3.1+build`); `^1.0`, `>=1` ou vazio são recusados.
12. **Contrato de módulo.** Classe abstrata com `name`, `version`,
    `indicator`, `plan(repo)` e `verify(repo) -> Check(ok, detail)`.
    `install` valida nome, versão e indicador e exige que o plano leve o
    nome e a versão do próprio módulo. `uninstall` é `revert` pelo nome.
    Indicadores pelos nomes de código: `first_try_success`, `rework`,
    `interventions`, `fixed_context_weight`, `dead_weight`, `adherence`,
    `freshness`, `cost_per_task`.
13. **Formato do arquivo de plano.** O mesmo dict de `Plan.to_dict`,
    com chaves em inglês (`module`, `version`, `operations`, `op`). É
    lido por quem escreve módulo, não pelo usuário final, e assim o
    manifesto repete a operação nas mesmas palavras do plano. Comando,
    opções (`--repositorio`) e mensagens em português.
14. **Nome do manifesto.** Um arquivo na raiz (`.dark-scaffold.json`), e
    não um diretório `.dark/`, para que o próprio manifesto não precise
    de posse de diretório.
15. **Códigos de saída do comando.** 0 feito ou nada a fazer; 1 conflito
    ou algo mantido; 2 entrada inválida (plano ilegível, versão não
    fixada, manifesto estranho).

## Quando a reversão não é byte a byte

Sem edição no meio, não encontrei caso. Além dos testes, rodei uma busca
aleatória fora do repositório (script no scratchpad, não versionado):
3000 sementes, cada uma com `.gitignore` e configuração JSON iniciais
sorteados (LF ou CRLF, com ou sem quebra no fim, indentação 2, 4, tab ou
compacta, `{ }` com espaço dentro), até três módulos com até cinco
operações cada, sobrepostas nos mesmos arquivos, diretórios e chaves,
revertidos em ordem aleatória. Em todas a árvore voltou idêntica por
hash, e depois de cada reversão os módulos restantes continuavam "já
aplicado". Essa busca é que achou o problema da necessidade
compartilhada (decisão 4).

Os casos que conheço, todos fora da promessa "sem edição no meio" ou
fora do conteúdo:

- **Metadados.** O conteúdo volta igual; o arquivo não é o mesmo
  objeto. A gravação por arquivo temporário e `os.replace` preserva o
  modo, mas troca o inode, quebra link físico (hard link), perde
  atributos estendidos e ACL, e muda a data de modificação. Dono e
  grupo podem mudar se o motor rodar com outro usuário.
- **Linha duplicada pelo usuário.** Se o usuário acrescentou de novo a
  mesma linha que o motor pôs, a reversão tira a última ocorrência, que
  pode ser a dele. O conteúdo fica com uma cópia, mas em outra posição.
- **Contêiner JSON que o usuário esvaziou de outro jeito.** Se o motor
  inseriu numa lista que já tinha um item do usuário e o usuário apagou
  esse item, a remoção do último filho deixa `[]`, não o espaço que
  havia lá antes da edição (que o motor não registrou, porque a lista
  não estava vazia).
- **Arquivo novo que outro módulo pede inteiro.** Se o módulo A cria um
  `.gitignore` acrescentando `x` e o módulo B pede `create_file
  .gitignore` com conteúdo `x\n`, B vê "já presente" sem registrar
  `shared` (as operações são diferentes) e reverter A apaga o arquivo de
  que B precisa. Não é perda de byte, mas é o único furo conhecido na
  reversão parcial. Correção possível: tratar como compartilhada qualquer
  operação "já presente" cujo alvo seja recurso possuído por outra
  entrada.

## O que o motor ainda precisaria para instalar um módulo real

- **Atualização de versão.** Hoje, aplicar `exemplo` 0.4.0 com o 0.3.1
  instalado soma as operações novas às antigas e conflita onde o valor
  mudou. Falta `upgrade`: reverter o que sumiu do plano, aplicar o que
  entrou, e trocar a versão das entradas que continuam.
- **Ações fora do repositório.** Instalar Langfuse ou Graphify exige
  baixar pacote, subir serviço ou rodar comando. O motor só edita
  arquivos do repositório. Falta uma operação de comando, com
  verificação e desfazer próprios, que não cabe na garantia byte a byte
  e precisaria de outra promessa (por exemplo, "desinstalar desfaz o que
  o comando registrou").
- **Verificação de verdade.** `verify` é só a interface. Um módulo real
  precisa testar que o servidor sobe, que o hook dispara, e devolver o
  motivo quando não.
- **Medida.** O contrato declara o indicador, mas não há ligação com a
  auditoria (antes e depois). Como este pacote não importa nada de `dark`,
  essa ligação fica para depois da renomeação do lote 007.
- **Arquivos de configuração com outra sintaxe.** JSONC, TOML e YAML
  (por exemplo, configuração de ferramenta de outra linguagem) não têm
  operação. O bloco com marcadores cobre texto livre, mas não entrada
  estruturada.
- **Configuração do usuário fora do repositório.** Alguns módulos vão
  querer `~/.claude/` ou similar. O motor recusa tudo fora do
  repositório por desenho; isso exigiria uma segunda raiz, com manifesto
  próprio.
- **Concorrência.** Duas execuções ao mesmo tempo no mesmo repositório
  podem se atropelar: não há trava no manifesto.
- **Entrada no `pyproject.toml`** para um comando `dark scaffold`, ou
  subcomando no `dark`, na junção.
